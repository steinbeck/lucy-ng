| Boundary | Description |
|----------|-------------|
| user CLI args (`paths`, `--out`) -> filesystem writes | User-controlled paths determine where JSON is written |
| `.dx` files in a discovered directory -> reader/decoder | Untrusted-ish scientific text files, any one of which may be malformed or hostile |
| QC verdict -> consumable `analysis/nmr_peaks/` | The single barrier preventing unvalidated peaks from becoming hard LSD constraints downstream |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-102-06 | Tampering | `--out` path traversal / writing outside the intended tree | mitigate | `Path(out_dir).resolve()` before any use (the established `cli/nus.py` convention); all writes go through `write_peak_json`, which only joins a fixed `{experiment}.json` name -- no user string is ever joined into the filename |
| T-102-07 | Denial of Service | Directory mode discovers an unbounded number of `.dx` files, or one file is malformed/truncated | mitigate | Per-file `try/except` around `JcampReader.read()` mirroring `nus/qc.py::_load_peaks`: one bad file is recorded in `failed` and the batch continues, but `failed` being non-empty forces a non-zero exit so it is never reported as a clean run. Total file count is bounded by the user's own directory -- accepted for a local CLI |
| T-102-08 | Tampering / Repudiation | D-07 write boundary: a FAIL verdict must never yield consumable peaks | mitigate | `out_root` is not created before the verdict is known; the FAIL branch writes only into `work_root/qc_failed/` (payloads + `qc_report.json`) and exits non-zero. Asserted end-to-end in plan 102-04 |
