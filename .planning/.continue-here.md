## Critical Anti-Patterns

Carried forward from the 2026-08-08 handoff (still true, all discovered through real
failure), plus three found this session.

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| **A broken measurement setup returns a plausible number, not an error** | Three times this session. (1) `ControlPath` over the 104-byte Unix-socket limit → eight ssh calls failed and the timing loop printed `0 ms`, which reads as "blazing fast". (2) An empty PID list reached `ps -p`, which then silently summed **all 969 processes** on the host — reported as "149 % CPU, 24 GB" for 38 webview servers. (3) `pgrep -f "lucy-ng:case"` found nothing on a host where two runs were healthily in progress, because resumed runs carry `--resume … -p Continue the in-progress CASE workflow` instead. | blocking | Every measurement needs a positive control: prove the setup reports the expected value in a case where the answer is known, before trusting it where it is not. A suspiciously clean number (0 ms, exactly 100 %, a round total) is a failure signal, not a result. |
| **A join that silently defaults to "confirmed"** | The audit workflow matched findings to their refutations on the verbatim quote string. Where the refuter had shortened a quote the join missed, and the code's fallback was `return true` — so **71 findings were reported as confirmed when 92 of 93 had in fact been refuted**. The number looked like a major result and was an artefact. Recomputed from the journal: one confirmed finding. | blocking | Never let a failed join default to the alarming branch. Cross-check any aggregate against the raw records (`journal.jsonl` for workflows) before reporting it. Arithmetic that does not add up — 93 raised, 92 refuted, 71 confirmed — is the tell. |
| **An empty list makes every comparison vacuous** | Four separate times on 2026-09-09: a `comm` against a file an ssh failure had left empty reported "no difference" (there was one, CASE189); `ps -p` with an empty PID list summed all 969 processes; a `pgrep` pattern that matched nothing read as a successful kill; two regexes over the protocols parsed 20 % and then 28 % of the rows and both looked like findings. | blocking | Assert non-empty before comparing. Print the input size next to the result. If a filter returns "nothing wrong", prove the filter can find something wrong. |
| **The pgrep pattern that matches nothing** | `pgrep -f "[u]atchdog\.py"` matches the literal "uatchdog.py" — but the file is `uat_watchdog.py`, so it matched nothing, `kill` got no argument, and the follow-up count (using the same broken pattern) reported "0 remaining". The launch script then correctly refused to start a second watchdog beside the survivor. An empty result and a successful kill look identical. | blocking | Bracket a letter that leaves the string intact: `[u]at_watchdog`. Verify a kill by PID, never by re-running the same pattern that produced the target list. |
| **The pgrep self-match trap, again** | On 2026-09-02 a check reported *five* watchdog instances where exactly one was running: the command line itself contained the literal `uat_watchdog.py` (inside a `grep -c "python3 -u scripts/uat_watchdog.py"`), so the shell matched its own process list. The bracket idiom in the *other* half of the same command was not enough. The project's own `uat_run_remaining.sh` has the same hazard: it guards with a bare `pgrep -f "uat_watchdog.py"`, so **invoking it from a command line mentioning that filename makes it refuse to start**. | blocking | Never let a process-matching command line contain the literal pattern anywhere — bracket every occurrence, or match on a PID list captured first. Cross-check any surprising count against `ps` on the specific PIDs. |
| **A quota reading can be badly wrong even when fresh** | On 2026-09-07 the snapshot file, freshly written both times, said **17 %** at 08:34 and **56 %** at 08:47. Thirty-nine points in thirteen minutes is not usage. The reported percentage lags and catches up in jumps, so the earlier apparent *drops* (38→4 on 09-05, 26→17 overnight) were lagging readings, not real decreases and not a changed plan. | blocking | Treat a single fresh reading as one noisy sample. The watchdog's extrapolation is often the better estimate — it measured 2.05 pt/h against the 2.0 it assumes. Never conclude a trend from two readings. |
| **Verifying a running process by reading its source file** | After changing `STALE_HARD_LIMIT_S` the check imported the *file* and printed "30 h" — proving nothing about the process, which had started before the edit and still held 12 h. Compounded by a kill that silently did nothing (see below), so the change was not live while being reported as done. | blocking | A constant is live only if the process started *after* the file's mtime. Compare the two explicitly, or restart and confirm from the process's own log line. |
| **Tests that spawn real processes** | The first revision of the opt-out tests called `serve` without patching `server.start`, leaving **eight live uvicorn servers** on the dev machine — while the feature under test existed to stop exactly that leak. | blocking | Patch the side-effecting entry point in a fixture shared by every test in the class, so no test can start a real server regardless of implementation state. Runtime is the tell: 4.35 s → 0.40 s once nothing spawned. |
| **Reading a stale planning doc as current fact** | `STATE.md` was reported to the user verbatim, including "CR-02/CR-03 filed, not fixed". Both had been fixed on 2026-08-03 in `7dfe2ce`. The file's own header date was wrong too. | blocking | Before citing a planning document as the current state, check it against git: `git log --since=<doc date>` for the paths it describes. The doc is a snapshot with a date, not a source of truth. |
| **Framing a settled decision as an open defect** | The benchmark's mixed provenance (two skill states, two team models) was written up as a to-do proposing re-runs. It was in fact a deliberate, discussed decision on cost grounds. | advisory | Before filing something as a defect, ask whether it was chosen. A trade-off someone accepted belongs in the decision record with its rationale, not in a to-do list that reopens it. |
| **Symptom-to-cause invention** (from 2026-08-08) | `Execution error` in a run log → declared the CLI broken, killed a healthy run, committed a false claim. It is what `claude -p` prints when `timeout` kills it. | blocking | Locate and read the code that emits the symptom before asserting a cause. Name the file and line. Without that you have a guess, not a cause. |
| **Grading against an unverified reference** (from 2026-08-08) | `NUS-RECONSTRUCTION-GUIDE.md` §8/§10 was cited as "ground truth" across three phases and two source modules. It is a prior agent's hypothesis about an unsolved sample, written into a failed run's own output directory. | blocking | Verify a reference's provenance where it is first cited — who produced it, from what, when. An artefact sitting in a run's own output directory is a suspect, not a source. |
| **Diagnosing long runs by elapsed time or log lines** (from 2026-08-08) | A CASE run takes 1.5–2.5 h and hits the 3600 s call timeout once per attempt by design. | advisory | Judge progress by artefacts appearing in `analysis/` (iteration dirs, `timing.jsonl`), never by log text or elapsed time. |

## How to restart the watchdog (this cost time twice)

`./scripts/uat_run_remaining.sh` — but **from a command line that does not contain the string
`uat_watchdog.py`**, or its own bare `pgrep -f` guard matches your shell and refuses to start.

Two things that do *not* work:

- Editing `scripts/uat_watchdog.py` alone. The running process holds the value it read at
  startup; a ceiling change needs a restart to take effect. Confirm it in the log — a fresh
  start prints `thresholds: 7d < NN %`.
- `launchctl kickstart -k`. The LaunchAgent runs the *launch script*, which detaches the
  watchdog (PPID 1), so kickstart never reaches the running process — it just logs
  "A watchdog is already running. Not starting a second."

The healthy state is a **pair**: the python process plus its `caffeinate -i -m` parent. On
2026-09-02 only the caffeinate half had been killed; the watchdog was still polling, so it
looked fine, but the Mac could then idle-sleep and stall it — which is exactly what cost
11.5 hours overnight on 2026-08-31.

## What the C20H32O2 re-analysis established (2026-09-05/06, not yet written up)

Reached from integrated ¹³C areas and edited-HSQC signs — an independent route to the same
answer the 2026-08-02 analysis got from weaker evidence:

- **The minor component is ~16.5 % of the ¹³C signal area, not 40 %.** The 40 % came from a ¹H
  integral whose normalisation was never checked.
- **The carbon list is not ambiguous after all.** Integrated areas separate the components:
  15 signals at ~1.0, one at **2.08** (22.63 ppm = two coincident carbons, confirming the user's
  own hypothesis and the earlier 2.02), 51.63 at 0.65, everything else ≤0.4. 15 + 2 + 1 plus the
  two olefinics from `exp7` = **exactly 20**.
- **51.63 is quaternary**, confirmed: its HSQC response is 45σ where every other carbon runs
  166σ–55 611σ, and it is isolated so nothing bleeds into it.
- **No weak carbon is a hidden quaternary** — every sub-0.4 signal shows a strong HSQC
  correlation, so they are protonated carbons of the minor component.
- **The CH₃/CH split needs no integral argument.** Six positive-sign carbons must carry
  32 − 22 = 10 H, and x·3 + (6−x)·1 = 10 forces x = 2. The formula decides it.
- Result: **11 CH₂ + 4 CH + 2 CH₃ + 3 Cq**.

Open: **35.23 ppm** has a full-carbon area (0.84) but an HSQC response of only 166σ, ~25× weaker
than comparable neighbours. Either a weak CH₂ correlation or a fourth quaternary; the H balance
argues for CH₂. And 13 of 39 signals sit closer than the HSQC's F1 resolution (0.088 ppm/point),
so those pairs cannot be separated at all.

⚠ Also measured: `zgpg30` with D1 = 2 s means NOE favours protonated carbons and quaternaries
are systematically weak. That is why "weak signal" and "quaternary" are hard to tell apart here.

Context worth keeping: all 5817 PubChem entries with formula C20H32O2 were checked. 66 match the
skeleton profile (4 rings, 1 C=C, no OH, no C=O), 34 as distinct constitutions — but **none**
matches the full carbon-type profile. That is not proof of novelty; a one-carbon error in the
assignment would change the hit list.
